Procédure d'installation cPanel — Kaeged GED

Déploiement pas à pas de la plateforme GED SaaS multi-tenant (Laravel 13 / PHP 8.4 / MySQL) sur un hébergement cPanel partagé.

Document lié : spec/cahier-des-charges-ged-saas-v1.0.docx (CDG §39 « Contraintes cPanel ») et docs/deploiement.md.

1. Prérequis

1.2 Informations à préparer

  • Nom de domaine (ex. ged.entreprise.com) et DNS pointant vers l'hébergement
  • Identifiants cPanel (ftp/ssh)
  • Nom de la base + utilisateur + mot de passe à créer (étape 2)
  • Adresse email pour les notifications (SMTP)

2. Créer la base de données

1Ouvrir l'assistant de base de données
cPanel → « Assistant Bases de données MySQL »
  1. Créer une base : kaeged_db (préfixe utilisateur automatique, ex. user_kaeged_db)
  2. Créer un utilisateur : kaeged_user + mot de passe fort
  3. Ajouter l'utilisateur à la base avec TOUS LES PRIVILÈGES

Noter : nom complet de la base (avec préfixe), utilisateur, mot de passe — nécessaires à l'étape 4.

3. Uploader le code

2Téléverser les fichiers
Gestionnaire de fichiers cPanel ou FTP
Règle de sécurité : le code applicatif (hors dossier public/) doit être placé hors de public_html pour ne pas être accessible en HTTP.
  1. Créer le dossier ~/kaeged (à côté de public_html)
  2. Uploader l'archive du projet (zip) dans ~/kaeged et l'extraire (ou uploader les fichiers via FTP)
  3. Structure attendue : ~/kaeged/app, ~/kaeged/bootstrap, ~/kaeged/config, ~/kaeged/public, ~/kaeged/routes, ~/kaeged/storage, ~/kaeged/vendor (après composer)…

4. Installer les dépendances (Composer)

3Lancer Composer
cPanel → Terminal (SSH)
cd ~/kaeged
composer install --no-dev --optimize-autoloader

Si Composer n'est pas disponible : téléverser composer.phar puis php composer.phar install --no-dev --optimize-autoloader.

En cas d'erreur « platform check » : vérifier que la version PHP sélectionnée dans MultiPHP est bien 8.4 (et que le terminal utilise le même PHP : php -v).

5. Configurer le fichier .env

4Créer et configurer .env
Gestionnaire de fichiers → ~/kaeged/.env
  1. Copier .env.example vers .env (ou uploader un .env préparé)
  2. Éditer les valeurs (voir modèle ci-dessous)
  3. Générer la clé : php artisan key:generate (terminal)
APP_NAME="Kaeged GED"
APP_ENV=production
APP_DEBUG=false
APP_URL=https://ged.entreprise.com

APP_LOCALE=fr
APP_FALLBACK_LOCALE=en

LOG_CHANNEL=stack
LOG_LEVEL=error

DB_CONNECTION=mysql
DB_HOST=localhost
DB_PORT=3306
DB_DATABASE=user_kaeged_db      # nom complet avec préfixe cPanel
DB_USERNAME=kaeged_user
DB_PASSWORD=********

SESSION_DRIVER=database
QUEUE_CONNECTION=database       # file d'attente en base (cPanel sans Redis)
CACHE_STORE=file
FILESYSTEM_DISK=local           # documents hors webroot (S3 en option)

# Sauvegardes
GED_MYSQLDUMP_PATH=mysqldump
GED_MYSQL_PATH=mysql

# Intégrations (optionnel)
# GED_STORAGE_DISK=s3           # si stockage objet
# MAIL_MAILER=smtp
# MAIL_HOST=smtp.entreprise.com
# MAIL_PORT=587
# MAIL_USERNAME=...
# MAIL_PASSWORD=...
# MAIL_FROM_ADDRESS=noreply@entreprise.com
Sécurité : ne jamais committer le .env ; le mot de passe de la base reste confidentiel.

6. Migrations & données initiales

5Créer les tables et le compte initial
cPanel → Terminal (SSH)
cd ~/kaeged
php artisan migrate --force
php artisan db:seed --force        # crée le super admin et le tenant démo (à supprimer en prod)
Production : supprimer le tenant « Entreprise Démo SA » et les comptes de démonstration après installation, puis créer vos tenants via le super admin.

7. Caches & permissions

6Optimiser et protéger
Terminal + Gestionnaire de fichiers
cd ~/kaeged
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan event:cache
  • Permissions : storage/ et bootstrap/cache/ en écriture (775 ou 755 selon l'hébergeur)
  • .env protégé : ajouter au .htaccess de ~/kaeged une règle de refus (ou s'assurer que le dossier est hors webroot)

8. Publier l'application (public_html)

7Pointer le domaine vers public/
Gestionnaire de fichiers

Deux options :

Option A — Contenu de public/ dans public_html (recommandée)

  1. Copier le contenu de ~/kaeged/public/ vers ~/public_html/ (index.php, .htaccess, robots.txt…)
  2. Éditer public_html/index.php : remplacer les chemins par ceux de ~/kaeged (l'index.php contient déjà les chemins relatifs — adapter __DIR__.'/../bootstrap/app.php' en '/home/user/kaeged/bootstrap/app.php')
  3. Créer le lien storage : php ~/kaeged/artisan storage:link puis copier ~/kaeged/public/storage vers ~/public_html/storage

Option B — Sous-dossier (si plusieurs apps)

Créer un sous-dossier public_html/ged et y placer le contenu de public/, adapter index.php en conséquence.

Le fichier .htaccess fourni par Laravel gère le routing et le blocage de l'accès aux fichiers sensibles.

9. Planifier les tâches (cron)

8Configurer le scheduler Laravel
cPanel → Tâches Cron

Ajouter une tâche toutes les minutes :

* * * * * /usr/local/bin/php /home/USER/kaeged/artisan schedule:run >> /dev/null 2>&1

Adapter /usr/local/bin/php au chemin PHP 8.4 de l'hébergement (vérifier avec which php en SSH) et /home/USER au chemin réel.

Le scheduler déclenche :

  • 02:00 — sauvegarde quotidienne (ged:backup, rétention 30 j)
  • 03:00 — rétention documentaire (ged:retention)
  • 06:00 — alertes de revue V02 (v02:review-alerts)
Alternative sans worker : la file en base (QUEUE_CONNECTION=database) + schedule:run suffit pour les volumes cibles (1000 utilisateurs, centaines de milliers de documents). Si les jobs deviennent fréquents, migrer vers un VPS avec worker Redis (CDG §39).

10. Sécurité & HTTPS

9Verrouiller l'installation
cPanel
  • HTTPS obligatoire : cPanel → « SSL/TLS » → certificat (Let's Encrypt automatique ou importé)
  • Forcer HTTPS : dans cPanel « Domains » ou via le .htaccess (redirection 301)
  • APP_DEBUG=false vérifié (aucun détail technique exposé)
  • Backups : configurer la sauvegarde de l'hébergeur + déporter les sauvegardes Kaeged (storage/backups) hors du disque mutualisé (FTP/S3)
  • Comptes : supprimer les comptes démo, forcer MFA sur le super admin
  • Permissions : vérifier que storage/app/private (documents) n'est jamais accessible via HTTP

Seuil d'escalade (CDG §39)

Si le mutualisé atteint ses limites (jobs asynchrones fréquents, stockage local > limites, recherche plein texte/vectorielle centrale, CPU/mémoire insuffisants) : migrer le cœur applicatif vers un VPS ou service managé en conservant l'architecture (queue Redis/worker, stockage S3 via GED_STORAGE_DISK=s3, moteur de recherche externe).
